# 架构设计

## 总体架构

shiro 前后端完全解耦，通过 HTTP API 通信。桌面版中 Electron 只是一个壳：启动时拉起后端进程，退出时一起回收。剧本编辑器类似 VSCode 打开项目文件夹：直接对照用户文件系统上的真实文件夹，文件夹是唯一权威数据源。后端是同一份代码，局域网内的设备（iPad、手机等）可通过浏览器直接访问，未来可直接部署为服务器版本。

```text
┌──────────────────────────────┐  ┌──────────────────────────────────┐
│  用户剧本文件夹（任意位置）      │  │         ~/.config/shiro/         │
│  正文 markdown / .shiro/ 元数据 │  │  db/ 内容库（明文）/ config.toml  │
└──────────────┬───────────────┘  └────────────────┬─────────────────┘
               │ 直接读写                            │ 读写
               ▼                                   ▼
┌─────────────────────────────────────────────────────────────────┐
│                       shiro-daemon (Rust)                       │
│  ┌────────────────────┐   ┌─────────────────┐                   │
│  │ 存储与管理           │   │ 模型接入          │                   │
│  │ 剧本项目/内容库      │   │ provider 抽象     │                   │
│  │                    │   │ SSE 流式          │                   │
│  └────────────────────┘   └─────────────────┘                   │
│       REST API (utoipa, OpenAPI schema)                         │
│       静态资源 serve（前端）                                      │
└──────────────────────────────┬──────────────────────────────────┘
                               │ HTTP
                 ┌────────────┼─────────────┐
                 ▼            ▼             ▼
           ┌──────────┐ ┌──────────┐ ┌──────────┐
           │ Electron │ │ 移动端     │ │ 服务器版   │
           │ 壳（桌面） │ │ 浏览器     │ │ （未来）   │
           └──────────┘ └──────────┘ └──────────┘
```

详见 [技术栈](./tech-stack.md) 与 [存储设计](./backend/storage.md)。

## 核心原则

**1. 前端只认识 HTTP API**

Web 前端不依赖 Electron IPC，只通过 REST API 通信。

**2. 后端不依赖 Electron**

后端是独立的 Rust 二进制，不依赖任何桌面端代码。

**3. API 契约先行**

REST API 由代码生成 OpenAPI schema（utoipa：`#[utoipa::path]` 标注端点、DTO derive `ToSchema`，路由与文档同一来源），固化于 `shiro-daemon/openapi.json`（改 API 后 `cargo run -- --dump-openapi > openapi.json` 重新固化，契约测试校验同步），TypeScript 类型从 schema 生成（`npm run gen:types`），前后端不允许手写对接口。

**4. 编辑计算归 app，存储与管理归 daemon**

**5. 模型接入归 daemon**

模型接入层在 shiro-daemon 内实现，见[模型接入设计](./backend/model-access.md)。

## 部署形态

### 桌面版（sidecar 模式）

Electron 壳与后端二进制一起打包发行（electron-builder 的 `extraResources`）：

```text
Electron 启动
  → 预选空闲环回端口 + 生成随机 token
  → spawn shiro-daemon 子进程（token 经环境变量传入，不落盘）
  → 轮询就绪端点 → 加载主界面
Electron 退出
  → 回收 shiro-daemon 子进程（防孤儿进程）
```

**本地 API 安全**：localhost 端口任何本机进程都能访问，所有请求必须携带启动时生成的随机 token。防护对象是浏览器里的恶意网页（CSRF 直写剧本库）——本机同权限进程可直接读写数据目录，等价绕过，不在防护范围。

### 局域网访问

daemon 直接 serve 前端静态资源，局域网内的设备（iPad、手机等）通过浏览器访问编辑器。这是「前端只认识 HTTP API + 后端独立」的直接兑现，不需要新的进程模型。

- 桌面版默认只监听 `127.0.0.1`，局域网访问是显式开启的开关（监听 `0.0.0.0`），开启后展示局域网地址
- 认证沿用 hawk 的「URL + KEY」模式：用户在桌面端 app 设置中生成或填写访问 key（256-bit 随机值，存 `~/.config/shiro/config.toml`），修改后旧 key 立即失效（401），无登录端点、无会话令牌
- 静态资源不鉴权（不含数据，数据全在 API 后面）；全部 `/api/*` 要求 `Authorization: Bearer <key>`，未带或错误返回 401，移动端首次打开时由前端展示 key 输入页，输入后存 localStorage
- SSE 走 `?key=` 查询参数（EventSource 无法自定义 header），daemon 以同一逻辑校验
- 桌面 app 自身继续使用启动时生成的随机 token（env 传入，不落盘，防本机恶意网页），鉴权中间件同时接受两种凭据
- 局域网模式使用明文 HTTP（内容不出内网）；模型 API key 只在 daemon 侧使用，不下发给前端
- 并发编辑采用单写者 + 乐观锁：保存带版本号，版本过期则拒绝并提示刷新；CRDT 协同列为后续项，暂不实现
- 文档被其他设备修改时，通过 SSE 通知前端提示刷新
- 移动端定位：碎片时间的改稿、阅读、记设定；连续长篇码字回桌面——不追求与桌面端对等的编辑体验（移动浏览器的键盘、IME、后台标签页挂起都是硬限制）

### 服务器版（未来）

同一个 shiro-daemon 部署在服务器上，为多个用户服务。与桌面版的差异：

| 差异点   | 桌面版                  | 服务器版           |
| -------- | ----------------------- | ------------------ |
| 访问范围 | 本机 + 局域网           | 公网               |
| 认证     | 随机 token + 局域网 key | 真实的用户认证体系 |
| 数据     | 单用户本地资料          | 多用户隔离         |

当前只实现桌面版与局域网访问，不提前实现服务器版的任何功能。

```text
shiro/
├── shiro-daemon/             ← Rust 后端（桌面版与服务器版共用）

├── tools/                    ← 仓库级脚本（构建/安装/冒烟/性能压测）
└── docs/                     ← 设计文档
```
